# Development environment

The repository is developed in a Dev Container (`.devcontainer/`) built from
`mcr.microsoft.com/devcontainers/dotnet:2-10.0-noble` with a PostgreSQL 18
sidecar. This page describes the pinned toolchain, how to provision it, and how
to validate it.

### Limitations

- **amd64 only.** Docker package versions were verified against the amd64
  package index only. The image build should fail fast on other architectures
  until the arm64 index is checked.
- **Docker client only.** No Docker daemon, `containerd`, privileged mode, or
  socket mount is configured. Having the `docker` CLI does not give access to a
  Docker host. Daemon access needs separate, explicit approval.
- Dev Container features run after the Dockerfile. Confirm after a rebuild that
  `node` still resolves to `/opt/node/bin/node`.

## Local configuration

PostgreSQL credentials come from `.devcontainer/.env`, which Git ignores. Create
it from the sample if no local file already exists:

```sh
cp -n .devcontainer/.env.example .devcontainer/.env
```

Then edit the placeholders. `cp -n` will not overwrite an existing `.env`. Never
commit, print, or share `.env`.

Changing `POSTGRES_*` values only affects a **new**, empty data volume. An
existing `postgres-data` volume keeps the credentials it was created with. Do not
run `docker compose down -v` or delete the volume to "reset" credentials without
explicit approval, because that destroys local data.

## Provisioning

Building the image and replacing the running dev container are separate,
user-approved actions. A rebuild can end the sessions running in the current
container.

### Lockfile

The lockfile is `.devcontainer/devcontainer-lock.json` (the CLI derives the name
from `devcontainer.json`; there is no `.devcontainer-lock.json`). Generate it without rebuilding using the official CLI, then verify the image on
a Docker-capable host from the repository root:

```sh
npx --yes @devcontainers/cli@0.90.0 upgrade --workspace-folder .
npx --yes @devcontainers/cli@0.90.0 build --workspace-folder .
npx --yes @devcontainers/cli@0.90.0 build --workspace-folder . --frozen-lockfile
```

Inspect the diff afterwards. The only expected change is a new `github-cli`
entry. Reject any change to the existing agent feature resolutions. Do not delete
the lockfile or write hashes by hand.

**Status:** lockfile generation passed. Both image-build commands remain unrun
because this session has no authorized Docker daemon access.

## Validation

### Without a rebuild

```sh
python3 -I -c 'import json, encodings, ssl, sqlite3'
dpkg -S /usr/lib/python3.12/json/__init__.py
python3 -m unittest discover -s tests -p 'test_agentic_flow.py' -v
git diff --check
git status --short
```

These checks cover the Python fix and the workflow tests. They do **not** show
that the image builds, which runtime versions are installed, whether the database
is healthy, or whether Docker can connect.

### After an approved rebuild

From the repository root:

```sh
python3 -I -c 'import json, encodings, ssl, sqlite3'
dotnet --version          # 11.0.100
node --version            # v24.22.2
npm --version             # 11.19.1
gh --version              # 2.103.3
docker --version          # 29.9.3
docker compose version    # 5.7.0
claude --version
codex --version
copilot --version
docker compose --env-file .devcontainer/.env.example \
  -f .devcontainer/docker-compose.yml config --no-env-resolution --quiet
```

Every command must exit 0 and report the expected version. The Compose check
uses the sample file and `--no-env-resolution`, so it does not read or print the
private `.env`.

On the host, compare the project-prefixed PostgreSQL volume name and creation
timestamp before and after the rebuild. They must be unchanged, and the existing
`db` service must report healthy. If there is no access to a Docker daemon,
report host validation as blocked. That is not a pass.

## Validation performed during implementation

The exact .NET and Node archives were downloaded, checksum-verified and executed
in an isolated temporary directory: SDK `11.0.100`, Node `v24.22.2` and npm
`11.19.1` passed. Matching Docker CLI `29.9.3` and Compose `5.7.0` packages were
also executed without a daemon. The sample-only Compose validation above passed.
Dev Container CLI `upgrade` generated the tracked lockfile without changing the
three existing agent feature entries. These checks do not replace an image build.

The installed Codex CLI was missing `codex-code-mode-host`; the matching official
`@openai/codex@0.167.1` npm distribution includes it. Its sandbox still requires
unprivileged user namespaces, which this running container does not permit.
Do not disable its sandbox or change host kernel policy automatically. Confirm
that the agent features provide all required execution binaries and that the
host permits the intended sandbox after rebuilding.
